# Push cut_v6 中文成品与审阅

复核日期：2026-09-21。API 已提交并冻结 **1 个新训练控制 policy、1 个 prior，
2 个数据/责任组、14 个片段**。24 次实际请求和返回均为 gpt-6-astra/xhigh，
51 个发布文件及原始数值切片通过验证。此前所有 cut 与 training_v3 保留。

本轮采用[通用 prompt](../prompts/general_cut_and_prior_v5.md)＋
[Push specific](../task_specifications/push_letters_v2.md)。按用户追加要求，
通用 prompt 在空间目标后顺带举了 `(e.g., a contact point)`，没有要求
一个 policy，也没有给定接触点的输出字段。本结果是带该例子的 API 设计。

## API 最终选择

| 数据/责任组 | 训练模型 | 数据用途 |
| --- | --- | --- |
| shape_push_decisions | 一个 shape_push_v1 | 12 个上下文片段，47 个明确的稀疏决策锚点 |
| geometric_motion_executor | 无 | 两条完整原始轨迹，保留连接运动、执行、上下文与结果证据 |

两条原轨迹的 16,745 行全部保留，没有原始记录排除。学习组物化了 16,715 行
（含片段重叠），但只有 47 个决策位置参与拟议监督：第一条 23 个，第二条
24 个。其余保留行用于历史、未来目标/接触推导、结果和执行器证据。
**47 个锚点尚不是 47 个已经验证有效的数值接触标签。**

API 的理由是：平移、转动、修正可用同一个“当前形状＋目标条件下选择局部推动”
的问题表达。连接路径交给已有执行器；小数据不支持再分多个独立专家。
它没有把不同字母、单词、换位或微调各训一个模型。

## 这个 policy 学什么

输入是当前选中物体的轮廓（包含内孔）、物体目标位姿、周围障碍、工作空间、
工具几何，以及最多三个因果几何历史。先把几何转换到以物体为中心、朝向目标
的平面坐标系。字母类别、目标单词和机器人关节指令不进入控制网络。
RGB 仍是上游观测来源，由拟议感知和几何预处理转换成这些输入。

输出是一个共同选择的局部推动方案：

- 物体侧边界上的二维接触点，单位米；不是 TCP 原点。
- 平面内推动方向。
- 一小段工具推动距离；不是承诺物体一定移动同样距离。
- 对应场景版本、候选排序、有效性和状态信息。

高度、工具姿态可行性、接近间隙、速度、守护条件及撤离由几何适配器和控制器
决定，不是网络学习的额外输出自由度。模型不输出完整六维 EE 轨迹。

API 提议在外轮廓和可访问内孔上采样 128 个接触候选，结合相对内法线的七种
方向和 5/10/20 mm 距离，经可行性过滤后由小型共享 MLP 评分。物体点编码器
和候选评分器分别使用两层 64 单元；这是架构设计，尚无实现参数量或权重。
短推动受 `min(20 mm, 0.2 × 物体直径)` 约束，并在最多约一秒后重新观察。

## Agent 与 planner 怎么调用

1. 从当前场景建立实例、轮廓、位置与不确定性，明确单词对应的物理布局。
2. Agent 选择物理实例及目标位置/朝向，调用 `propose_push`。
3. planner/controller 用返回的接触方案执行 `prepare`；到达后重看或重算方案。
4. 执行一次受约束的短 `push`，重新观察物体误差，选择继续推、换接触点或换物体。
5. `withdraw/view/hold` 等由执行器提供。已经处于有效接触时，可直接继续局部推动，
   不要求每次先抬起来。

API 给出了 `proposed/already_at_goal/needs_view/no_safe_candidate/stale_scene`
等策略状态，以及执行器的到达、完成、接触丢失、中断等反馈。工具到达接触点
与物体达到任务目标分别判定。高层调用和执行器接口已经有可查阅的设计文档：

- [Policy 调用目录](../data/push_letters/cut_v6/POLICY_CATALOG.md)
- [完整执行分工与调用契约](../data/push_letters/cut_v6/EXECUTION_CATALOG.md)
- [Policy prior、输入、目标推导与全部片段](../data/push_letters/cut_v6/datasets/shape_push_decisions/heuristic.md)

这些是拟议接口，没有新 policy 函数、模型训练或真实 planner binding。

## 我的判断与目前的缺口

本轮明显更接近用户要试的分工：学习集中在物体相对的接触与二维局部运动，
连接动作由已有执行能力完成；抬起不再是 learned policy 的输出维度。
实际执行器仍可能为接近、避障或退出而抬起，需要正确实现其模式与约束。
输出约束和模型缩小使学习目标更明确，不能据此断言已经能泛化。

最关键的问题转为**标签质量与在线感知**：

- API 只挑出 47 个决策点。它要求标定桌面、物体高度和真实工具接触面，审核
  物体 mask/track，再从未来片段反推接触点及第一个有效短推动。拟议无效标签
  要屏蔽并报告数量，因此最终有效样本可能少于 47。
- 离线审核的轮廓/目标与在线自动感知之间仍可能存在差异。API 要求部署端用
  因果感知替代离线标注；这个替代尚未实现和验证。
- “一个 policy”具体指一个新训练的控制网络。API 另提议两个**外部冻结感知
  依赖**：SAM 2.1 Hiera-small 用于 mask/传播，Qwen2.5-VL-7B-Instruct 用于
  身份与朝向假设；它们目前不是已下载、已集成或已验证的资产。
- 接触过程的线段跟踪、目标物接触许可、内孔插入、停止反馈需要实际执行器
  支持。已有 motion planner 的能力声明并不等于这些适配已经完成。
- 未知物理字母、材质和新单词的泛化仍需独立试验。两条示范与这一轮设计
  不能给出成功率或相比旧模型更好的实测结论。
